MARCO DE LA UNIDAD

Seguridad durante todo el ciclo de vida

Una aplicación web está formada por código, datos, identidades, dependencias y servicios desplegados. La seguridad funciona mejor cuando cada parte se protege y se verifica de forma continua.

Reducir vulnerabilidades

Validar entradas, controlar permisos y evitar exponer información o componentes innecesarios.

Proteger el acceso

Gestionar correctamente autenticación, autorización, sesiones y secretos.

Detectar y corregir

Analizar la aplicación, observar registros y confirmar que las correcciones funcionan.

Ciclo de seguridad de una aplicación

Uso responsable: las pruebas activas y los análisis se realizan solo sobre sistemas propios o con autorización explícita, con alcance definido y preferiblemente en un entorno de pruebas.

BLOQUE 01 / 04

1. Amenazas y vectores web

Para proteger una aplicación, primero identificamos dónde entra la información, qué puede hacer cada usuario y qué datos quedarían expuestos si algo falla.

1.1 Familias de riesgos en aplicaciones web

OWASP Top 10 agrupa riesgos frecuentes para ayudar a priorizar. No es una lista exhaustiva ni reemplaza el análisis del contexto de cada aplicación.

Inyección

Datos externos llegan a una consulta o intérprete como si fueran instrucciones. La defensa principal es separar datos de código, por ejemplo, mediante consultas parametrizadas.

XSS

Contenido no confiable se interpreta como código en el navegador. Se reduce con escape de salida según contexto y políticas CSP como defensa adicional.

Control de acceso

La aplicación confía en un identificador o rol enviado por el cliente. Cada operación debe comprobar en el servidor si ese usuario puede actuar sobre ese recurso.

CSRF y sesiones

Una sesión débil o una petición no protegida puede permitir acciones no deseadas. Se combinan tokens CSRF, cookies seguras y validaciones del origen según el caso.

SSRF y acceso a recursos

La aplicación puede ser inducida a solicitar destinos que no debería alcanzar. Limita destinos permitidos y controla las salidas de red desde el servidor.

Configuración y componentes

Servicios expuestos, dependencias vulnerables, permisos excesivos o valores por defecto aumentan la superficie de ataque.

1.2 De una entrada no confiable a una consulta segura

Una consulta debe mantener separada la estructura SQL del valor proporcionado por la persona usuaria. La parametrización permite que el controlador trate ese valor como dato.

Patrón que se debe evitar

Construir la consulta concatenando directamente una entrada:

query = "SELECT * FROM users WHERE id = " + user_input

El riesgo aparece cuando un valor de entrada puede modificar la estructura de la consulta.

Patrón recomendado

Usar una consulta parametrizada:

cursor.execute(
    "SELECT * FROM users WHERE id = ?",
    (user_id,)
)

El marcador puede variar según la biblioteca; consulta su documentación y valida también tipo, formato y permisos.

1.3 Exposición de datos y errores

Fuentes habituales

  • Mensajes de error que revelan rutas, consultas o versiones.
  • Copias de seguridad y ficheros temporales en directorios públicos.
  • Almacenamiento en nube con permisos públicos no previstos.
  • Credenciales, tokens o datos personales en código y registros.

Medidas sencillas

  • Mostrar errores generales al usuario y conservar el detalle en registros protegidos.
  • Separar copias y secretos del directorio público de la web.
  • Revisar quién puede acceder a cada contenedor o recurso.
  • Limitar y enmascarar datos sensibles en logs.
Idea clave: los datos que la aplicación no necesita exponer no deben estar disponibles por comodidad, por un error detallado ni por una configuración predeterminada.

2.2 Caso real: la brecha de Equifax (2017)

En 2017, atacantes aprovecharon una vulnerabilidad crítica de Apache Struts en un sistema de Equifax. El incidente expuso información personal de aproximadamente 147 millones de personas. Apache había publicado un aviso de seguridad con versiones corregidas.

Qué enseña el caso

  • Componente: Apache Struts, usado para procesar solicitudes de la aplicación.
  • Debilidad: CVE-2017-5638 afectaba a ciertas versiones del componente.
  • Lección: inventariar dependencias, revisar avisos y desplegar parches con rapidez.

Ejemplo defensivo: actualizar la dependencia vulnerable

Versión afectada del ejemplo

<dependency>
  <groupId>org.apache.struts</groupId>
  <artifactId>struts2-core</artifactId>
  <version>2.3.31</version>
</dependency>

Esta versión está dentro del rango vulnerable descrito en el aviso de Apache para CVE-2017-5638.

Versión corregida indicada por Apache

<version>2.3.32</version>

Apache también publicó la corrección en la rama 2.5.10.1. En un proyecto real, verifica compatibilidad, pruebas y avisos vigentes antes de actualizar.

Idea clave: el ejemplo muestra cómo identificar y corregir una dependencia vulnerable; no incluye instrucciones ni cargas para explotar el fallo.

Antes de probar

  • Define propietario, dominio, aplicaciones y fechas autorizadas.
  • Utiliza un entorno aislado con datos ficticios siempre que sea posible.
  • Acuerda límites, técnicas permitidas, contactos y condiciones de parada.

Al analizar

  • Empieza con observación y herramientas en modo seguro.
  • Confirma manualmente los hallazgos sin acceder a datos ajenos ni modificarlos.
  • Registra hora, alcance, evidencia saneada e impacto potencial.

El permiso importa: no analices ni pruebes sistemas públicos, cuentas o redes que no estén dentro del alcance autorizado. Una prueba de seguridad no requiere demostrar daño para documentar un riesgo.

BLOQUE 03 / 04

3. Medidas de protección

Las defensas se combinan: navegador, aplicación, identidad, infraestructura y proceso de despliegue.

3.1 Cabeceras de seguridad: instrucciones al navegador

HSTS

Indica al navegador que use HTTPS durante un periodo. Actívala cuando HTTPS funcione correctamente en todo el alcance indicado.

CSP

Limita desde dónde puede cargar recursos la página. Ayuda a reducir el impacto de inyecciones, pero debe ajustarse a los recursos legítimos de la aplicación.

Otras cabeceras

X-Content-Type-Options: nosniff evita interpretar tipos de contenido de forma inesperada. frame-ancestors controla quién puede incrustar la página.

Ejemplo inicial de Content Security Policy

Content-Security-Policy:
  default-src 'self';
  object-src 'none';
  base-uri 'self';
  frame-ancestors 'none'

Esta política es un punto de partida restrictivo, no una configuración universal. Prueba primero en modo de solo reporte y ajusta las fuentes necesarias sin permitir recursos indiscriminadamente.

Atributos que reducen riesgo

  • Secure: enviar la cookie solo por HTTPS.
  • HttpOnly: impedir su lectura desde JavaScript.
  • SameSite: limitar el envío en solicitudes entre sitios.

Ciclo de vida

  • Usa identificadores impredecibles y evita exponerlos en URL o logs.
  • Rota el identificador después de autenticar o cambiar privilegios.
  • Invalida la sesión al cerrar sesión y aplica expiración adecuada.

Ejemplo ilustrativo de cookie de sesión

Set-Cookie: __Host-session=<token>; Path=/; Secure; HttpOnly; SameSite=Lax

El nombre __Host- requiere HTTPS, ruta raíz y ausencia del atributo Domain. El token debe generarse de forma segura en el servidor; nunca escribas su valor real en documentación.

3.3 Autenticación, autorización y abuso automatizado

Autenticación

Responde: «¿quién eres?». MFA añade un factor independiente y dificulta el acceso si una contraseña se filtra.

Autorización

Responde: «¿qué puedes hacer?». Comprueba los permisos en cada operación y recurso, no solo en la interfaz.

Rate limiting

Limita la frecuencia de acciones, como inicios de sesión o recuperación de cuenta, sin sustituir el control de acceso.

ModeloDecisión basada enEjemplo sencillo
RBACRol asignado a la persona.El rol «editor» puede publicar contenido.
ABACAtributos de persona, recurso, acción y contexto.Permitir editar un documento solo a su responsable dentro del equipo autorizado.

CAPTCHA puede ayudar frente a automatización en algunos flujos, pero no sustituye MFA, límites de frecuencia, detección de abuso ni una buena gestión de contraseñas.

3.4 Despliegue: contenedores, secretos e inventario

Contenedores más seguros

  • Usa imágenes base mantenidas y mínimas.
  • Ejecuta el proceso con usuario no privilegiado cuando sea posible.
  • Actualiza, analiza y limita capacidades y puertos.
  • Despliega artefactos revisados e imágenes verificables.

Secretos y SBOM

  • No incluyas contraseñas o claves en el código ni en la imagen.
  • Usa un gestor de secretos con acceso mínimo y rotación.
  • Genera un SBOM para conocer componentes y versiones.
  • Revisa avisos de seguridad y actualiza dependencias afectadas.

4. Registros, alertas e informes

Los registros aportan contexto para detectar e investigar. Un informe convierte los hallazgos en acciones que pueden priorizarse y verificarse.

4.1 De los eventos a una alerta útil

Aplicación y servicioseventos
→
Recolectornormaliza
→
Análisiscorrelaciona
→
Alertainvestigar y responder

Eventos que aportan contexto

  • Inicios de sesión satisfactorios y fallidos.
  • Cambios de permisos, configuración o factores MFA.
  • Errores de la aplicación y respuestas inusuales.
  • Creación de cuentas, tokens o recursos públicos.

Patrones que merecen revisión

  • Aumento de errores de autenticación en poco tiempo.
  • Acceso a muchos recursos que no son habituales para la cuenta.
  • Cambios administrativos fuera de ventanas esperadas.
  • Errores repetidos o picos de solicitudes anómalos.

Protege los logs: no registres contraseñas, tokens de sesión ni datos personales innecesarios. Restringe accesos, define retención y conserva integridad y marcas de tiempo.

4.2 Comunicar un hallazgo con claridad

Un hallazgo debe poder entenderse, priorizarse y reproducirse de manera segura. Describe las condiciones y el impacto sin incluir datos sensibles innecesarios.

Estructura de un hallazgo

  1. Título y activo afectado.
  2. Descripción: qué se observó y en qué condiciones.
  3. Impacto y riesgo: probabilidad y consecuencias.
  4. Evidencia: solicitud o registro saneado.
  5. Recomendación: acción concreta de corrección.
  6. Verificación: prueba posterior que demuestra la mejora.

Ejemplo breve

Hallazgo: no se observa una política CSP en la respuesta de prueba.

Riesgo: falta una capa de defensa frente a contenido no previsto; el riesgo real depende de cómo se procese la entrada en la aplicación.

Recomendación: definir una política ajustada a los recursos legítimos, probarla en modo de reporte y volver a revisar la respuesta.

4.3 Priorizar, corregir y verificar

Priorizar

Considera impacto, probabilidad, exposición, datos afectados y controles existentes. Una puntuación orienta; no sustituye el contexto.

Corregir

Asigna responsable y plazo, aplica el cambio y registra qué componente o configuración se modificó.

Verificar

Repite la comprobación que detectó el problema y confirma que la corrección no rompe la función legítima.

Regla práctica: un informe útil no termina con «se encontró un problema»; deja claro quién puede actuar, qué cambio se propone y cómo se comprobará el resultado.
CIERRE

Una aplicación web segura se mantiene

01 · Diseñar

Comprender las entradas, los activos, los flujos y los permisos reduce riesgos desde el origen.

02 · Verificar

Combinar análisis estático, dinámico y de dependencias mejora la cobertura, pero los resultados requieren revisión.

03 · Mejorar

Registros protegidos, informes claros y pruebas posteriores convierten los hallazgos en mejoras continuas.

Recuerda

Proteger no es añadir una única herramienta: es reducir exposición, comprobar permisos, cuidar secretos, observar el comportamiento y corregir con evidencia.

CSP
Política que restringe las fuentes de recursos que puede cargar una página web.
CSRF
Solicitud no deseada que aprovecha la sesión activa de una persona usuaria.
DAST

MFA
Autenticación multifactor que combina más de una prueba de identidad.
RBAC
Control de acceso basado en roles asignados.
SAST
Análisis estático de código o artefactos sin ejecutar la aplicación.
SCA
Análisis de composición de software y dependencias de terceros.
SBOM
Inventario legible de componentes de software incluidos en un producto.
SSRF
Riesgo de que una aplicación realice solicitudes a destinos no previstos.
XSS
Ejecución de contenido no confiable en el contexto del navegador de otra persona usuaria.
