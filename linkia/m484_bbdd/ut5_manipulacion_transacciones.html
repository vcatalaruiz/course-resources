Manipular datos: DML

El Lenguaje de Manipulación de Datos permite añadir registros, cambiar valores y eliminar filas. Las sentencias principales de esta unidad son INSERT, UPDATE y DELETE.

Sentencia Acción Precaución
INSERT Añade filas nuevas. Valores y columnas deben corresponderse.
UPDATE Modifica filas existentes. Usa WHERE para limitar las filas.
DELETE Elimina filas. Usa WHERE para evitar un borrado masivo.

La estructura de la tabla permanece después de un DELETE. En cambio, TRUNCATE es una operación distinta y su comportamiento transaccional depende del gestor.

Insertar registros con INSERT

Indica explícitamente las columnas para que la relación entre cada columna y su valor resulte clara. Respeta los tipos de dato, las claves y las restricciones de la tabla.

-- Añade un empleado indicando los campos que se van a rellenar.
INSERT INTO empleados (id, nombre, puesto, salario, id_departamento)
VALUES (101, 'Laura Sánchez', 'Administrativa', 1900, 2);

-- Añade varios productos en una sola sentencia.
INSERT INTO productos (id, nombre, precio)
VALUES
    (1, 'Ratón óptico', 12.50),
    (2, 'Teclado mecánico', 45.00);

-- Copia a una tabla de historial los clientes que ya han causado baja.
INSERT INTO historial_clientes (id, nombre)
SELECT id, nombre
FROM clientes
WHERE baja = 1;

El ejemplo usa nombres ilustrativos. Comprueba el esquema real y los campos obligatorios antes de adaptar una inserción a bd_empresa.

Actualizar y eliminar con condiciones

UPDATE modifica los campos indicados en las filas seleccionadas. DELETE elimina las filas que cumplen la condición.

-- Aumenta un 5 % el salario de quienes trabajan en Barcelona.
UPDATE empleados
SET salario = salario * 1.05
WHERE ciudad_trabajo = 'Barcelona';

-- Elimina clientes que tienen registrada una fecha de baja.
DELETE FROM clientes
WHERE fecha_baja IS NOT NULL;

Sin WHERE, UPDATE puede cambiar todas las filas y DELETE puede borrarlas todas. Antes de ejecutar una operación importante, prueba la misma condición con un SELECT y revisa las filas devueltas.

Integridad de los datos relacionados

La integridad referencial mantiene coherentes las relaciones entre tablas. Una clave foránea referencia una clave primaria y solo acepta los valores permitidos por la relación.

  • Integridad de entidad: cada fila se identifica de manera única y la clave primaria no es nula.
  • Integridad de dominio: los datos cumplen el tipo y las restricciones del campo.
  • Integridad referencial: una clave foránea apunta a una fila existente o admite NULL cuando el diseño lo permite. 
-- Relaciona cada empleado con un departamento existente.
CREATE TABLE empleados (
    id INT PRIMARY KEY,
    nombre VARCHAR(50),
    id_departamento INT,
    FOREIGN KEY (id_departamento) REFERENCES departamentos(id)
);

-- Evita que el salario tenga valores negativos.
ALTER TABLE empleados
ADD CONSTRAINT chk_salario_no_negativo CHECK (salario >= 0);

Si id_departamento no admite NULL, cada empleado debe referirse a un departamento válido. Confirma las restricciones reales antes de insertar o modificar datos. En MySQL, las restricciones CHECK se aplican a partir de la versión 8.0.16.

Qué ocurre al cambiar una fila relacionada

Las reglas ON DELETE y ON UPDATE definen cómo se comporta la relación cuando cambia la fila referenciada.

Regla Efecto Condición o precaución
CASCADE Propaga el cambio a las filas relacionadas. Un borrado en cascada puede eliminar muchas filas dependientes.
SET NULL Establece la clave foránea en NULL. La columna debe permitir NULL.
RESTRICT / NO ACTION Impide el cambio si hay filas dependientes. El detalle temporal depende del gestor.

Comprueba primero cuántas filas dependen del registro padre. ON DELETE CASCADE puede eliminar todos esos registros; úsalo solo cuando ese sea el comportamiento deseado.

Transacciones: una unidad de trabajo

Una transacción agrupa varias operaciones que deben completarse como conjunto. Sirve, por ejemplo, para que una transferencia no reste dinero de una cuenta sin añadirlo a la otra.

-- Transfiere 100 € entre dos cuentas como una sola operación lógica.
START TRANSACTION;

UPDATE cuentas
SET saldo = saldo - 100
WHERE id = 'A';

UPDATE cuentas
SET saldo = saldo + 100
WHERE id = 'B';

COMMIT;

Las transacciones requieren tablas con un motor transaccional, como InnoDB. Si la validación falla, decide el ROLLBACK antes de confirmar. No dejes transacciones abiertas.

Confirmar, deshacer y crear puntos de control

  • START TRANSACTION o BEGIN inicia el bloque.
  • COMMIT hace definitivos sus cambios.
  • ROLLBACK revierte los cambios aún no confirmados.
  • SAVEPOINT crea un punto intermedio al que se puede volver.
-- Cambia una ciudad y revierte el cambio durante la demostración.
START TRANSACTION;

UPDATE empleados
SET ciudad_trabajo = 'Zaragoza'
WHERE id = 101;

SELECT id, ciudad_trabajo
FROM empleados
WHERE id = 101;

ROLLBACK;

-- En otra ejecución controlada, confirma una operación válida.
START TRANSACTION;

UPDATE empleados
SET ciudad_trabajo = 'Zaragoza'
WHERE id = 101;

COMMIT;

En modo autocommit, el gestor puede confirmar cada sentencia automáticamente. Confirma el modo de trabajo y el motor de almacenamiento antes de probar ROLLBACK.

Savepoints: deshacer solo una parte

Un punto de control permite revertir parte de una transacción sin deshacer necesariamente las operaciones anteriores. La transacción sigue pendiente hasta COMMIT o ROLLBACK. 

-- Conserva el primer cambio y revierte solo el segundo.
START TRANSACTION;

UPDATE empleados
SET salario = salario + 100
WHERE id = 101;

SAVEPOINT despues_del_aumento;

UPDATE empleados
SET ciudad_trabajo = 'Zaragoza'
WHERE id = 101;

ROLLBACK TO SAVEPOINT despues_del_aumento;

COMMIT;

Los savepoints y su sintaxis pueden variar según el gestor. No se debe asumir que una sentencia de definición de estructura, como ALTER TABLE, pueda deshacerse como una operación DML.

Las cuatro propiedades ACID

Propiedad Qué garantiza Ejemplo intuitivo
Atomicidad Todo el bloque se aplica o nada se aplica. La transferencia no queda a medias.
Consistencia Se respetan las reglas y restricciones. No se guarda una FK inexistente.
Aislamiento Las operaciones concurrentes no producen resultados incompatibles. Una lectura no ve cambios sin confirmar.
Durabilidad Los cambios confirmados persisten ante fallos. Un COMMIT sobrevive al reinicio.

La base de datos y el motor de almacenamiento deben ofrecer soporte transaccional para que estas garantías se apliquen a las operaciones realizadas.

Atomicidad y consistencia

Atomicidad

Si falla una operación de una transacción, se pueden revertir también las operaciones anteriores del mismo bloque.

Consistencia

Una transacción debe respetar claves, tipos y demás restricciones que mantienen válidos los datos.

-- La clave foránea impide asociar la fila a un departamento inexistente.
INSERT INTO empleados (id, nombre, id_departamento)
VALUES (100, 'Jorge', 999);

Si la fila padre no existe, la restricción debe impedir la inserción. La respuesta concreta (error o gestión de la transacción) depende del gestor y de la sentencia ejecutada.

Aislamiento y durabilidad

  • Aislamiento: determina qué cambios de otras transacciones son visibles mientras una transacción está en curso.
  • Durabilidad: los cambios confirmados quedan registrados para mantenerse tras un fallo del sistema.
-- Confirma el cambio; después, comprueba que sigue registrado.
START TRANSACTION;

UPDATE empleados
SET activo = 0
WHERE fecha_baja IS NOT NULL;

COMMIT;

SELECT id, activo
FROM empleados
WHERE fecha_baja IS NOT NULL;

La durabilidad describe el compromiso del gestor una vez emitido COMMIT. Para comparar resultados, asegúrate de que las sesiones trabajan con los mismos datos y que una transacción anterior no está pendiente.

Concurrencia: varias sesiones a la vez

En un sistema multiusuario, varias transacciones pueden leer o cambiar datos simultáneamente. El motor coordina esas operaciones para reducir inconsistencias y conflictos.

  • Dos actualizaciones sobre un mismo valor pueden sobrescribirse.
  • Una lectura podría observar un cambio que después se deshace.
  • Una consulta repetida puede devolver valores o filas diferentes.
  • Un bloqueo puede hacer que una sesión espere a que otra termine.

El aislamiento y los bloqueos regulan qué interacciones se permiten; una transacción breve y un orden de acceso consistente ayudan a limitar contenciones.

Problemas que puede producir la concurrencia

  • Lectura sucia: se lee un cambio no confirmado que luego se revierte.
  • Lectura no repetible: una fila vuelve a leerse con un valor distinto tras una modificación de otra transacción.
  • Lectura fantasma: al repetir una consulta por condición, aparecen o desaparecen filas por cambios concurrentes.
  • Actualización perdida: una escritura posterior sobrescribe el cambio de otra sesión.
-- Dos sesiones leen el mismo saldo; la segunda escritura puede sobrescribir la primera.
SELECT saldo FROM cuentas WHERE id = 'X';

-- Sesión A escribe el saldo calculado desde 1000.
UPDATE cuentas SET saldo = 900 WHERE id = 'X';

-- Sesión B escribe su propio saldo calculado desde el mismo valor inicial.
UPDATE cuentas SET saldo = 950 WHERE id = 'X';

Este ejemplo describe dos sesiones que calculan un valor y luego lo escriben. El orden real de las operaciones, los bloqueos y el aislamiento determinan si el conflicto puede ocurrir.

Niveles de aislamiento

El estándar SQL define niveles que equilibran protección frente a anomalías y concurrencia. El comportamiento exacto puede variar entre motores.

Nivel Lectura sucia No repetible Fantasma
READ UNCOMMITTED Puede ocurrir Puede ocurrir Puede ocurrir
READ COMMITTED Evita Puede ocurrir Puede ocurrir
REPEATABLE READ Evita Evita Depende del motor
SERIALIZABLE Evita Evita Evita

La tabla resume el modelo ANSI; no predice por sí sola todos los comportamientos de MySQL, PostgreSQL u otros gestores. Comprueba la documentación del motor y el nivel configurado.

Bloqueos compartidos y exclusivos

Bloqueo Permite Limita
Compartido Varias lecturas compatibles. Escrituras incompatibles mientras se mantenga el bloqueo.
Exclusivo Una operación que modifica los datos. Lecturas o escrituras conflictivas de otras sesiones.
De fila Bloquea los registros afectados. Solo impide operaciones en conflicto sobre esos registros.
De tabla Restringe el acceso a la tabla completa. Puede bloquear operaciones no relacionadas con la fila modificada.

Bloquear una fila para modificarla

Un bloqueo exclusivo protege la fila seleccionada mientras la transacción decide si confirma o revierte el cambio.

-- Bloquea una fila y libera el bloqueo al confirmar.
START TRANSACTION;

SELECT id, salario
FROM empleados
WHERE id = 101
FOR UPDATE;

COMMIT;

FOR UPDATE se usa dentro de una transacción y su soporte depende del gestor. LOCK TABLES tiene particularidades; en MySQL puede implicar una confirmación implícita. No mezcles ambos mecanismos sin revisar la documentación del motor.

Interbloqueos y buenas prácticas

Un deadlock ocurre cuando dos transacciones esperan recursos retenidos entre sí. El motor puede detectar el ciclo y cancelar una de las operaciones para que la otra continúe.

Cómo reducir el riesgo

  • Mantén las transacciones breves y confirma o revierte cuanto antes.
  • Accede a las tablas y filas en el mismo orden desde procesos distintos.
  • Elige un nivel de aislamiento adecuado al trabajo.
  • Usa condiciones e índices apropiados para evitar lecturas innecesariamente amplias.
  • Prepara la aplicación para volver a intentar una transacción cancelada de forma segura.

¿Qué has aprendido?

  • INSERT, UPDATE y DELETE manipulan los registros.
  • Una clave foránea y sus acciones mantienen coherentes las tablas relacionadas.
  • BEGIN, COMMIT y ROLLBACK controlan una transacción.
  • ACID resume las garantías de atomicidad, consistencia, aislamiento y durabilidad.
  • El aislamiento y los bloqueos ayudan a controlar la concurrencia y sus anomalías.

Glosario esencial

  • DML: instrucciones para insertar, modificar y eliminar datos.
  • Clave foránea: campo que relaciona una tabla con otra.
  • Transacción: conjunto de operaciones que se confirma o se deshace.
  • ACID: propiedades de atomicidad, consistencia, aislamiento y durabilidad.
  • Lectura sucia: lectura de un cambio todavía no confirmado.
  • Lectura fantasma: nuevas filas aparecen en una consulta repetida.
  • Deadlock: ciclo de espera entre transacciones que retienen recursos.

Actividad 2: integridad referencial

Ejemplo guiado: comportamiento de SET NULL

-- Define una relación que desvincula a los empleados si se elimina su departamento.
ALTER TABLE empleados
DROP FOREIGN KEY fk_empleado_departamento;

ALTER TABLE empleados
ADD CONSTRAINT fk_empleado_departamento
FOREIGN KEY (id_departamento)
REFERENCES departamentos(id)
ON DELETE SET NULL;

-- Comprueba qué empleados dependen del departamento antes de probar el borrado.
SELECT id, nombre, id_departamento
FROM empleados
WHERE id_departamento = 2;

La columna id_departamento debe permitir NULL para usar SET NULL. Antes de modificar la restricción existente, averigua su nombre real y revisa el esquema de la base.

Actividad 3: transacciones y control de errores

Ejemplo guiado: comprobar y decidir

-- Cambia temporalmente el salario y comprueba el valor antes de decidir.
START TRANSACTION;

UPDATE empleados
SET salario = salario - 100
WHERE id = 101;

SELECT id, salario
FROM empleados
WHERE id = 101;

-- Ejecuta COMMIT si el resultado es correcto; en caso contrario, ejecuta ROLLBACK.
ROLLBACK;

La decisión entre COMMIT y ROLLBACK se toma después de revisar el resultado. No ejecutes ambos como parte de la misma prueba ni uses bloques IF de rutinas almacenadas como si fueran SQL interactivo.

Actividad 4: concurrencia, bloqueos y ACID

Enunciado: simula dos sesiones que actualizan el mismo salario, aplica los niveles READ COMMITTED y SERIALIZABLE, usa LOCK TABLE empleados WRITE y analiza su impacto, describe un caso real que incumpla una propiedad ACID y demuestra una lectura fantasma.

Entrega: archivo SQL y PDF con pasos de cada sesión, capturas y justificación.

Guía de simulación

  1. Abre dos sesiones independientes conectadas a una base de pruebas.
  2. Usa una fila identificable y anota el valor inicial antes de iniciar los cambios.
  3. Repite el mismo caso con ambos niveles de aislamiento y registra cuándo puede leer o escribir cada sesión.
  4. Para la lectura fantasma, repite una consulta por rango mientras la segunda sesión inserta una fila que cumpla ese rango.
  5. Documenta esperas, errores y resultados; libera cualquier bloqueo al terminar.

Sesión A: leer la fila con READ COMMITTED

-- Abre una transacción y lee el salario antes de que lo cambie la otra sesión.
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;

SELECT id, salario
FROM empleados
WHERE id = 101;

Sesión B: modificar el mismo registro

-- Cambia el salario mientras la transacción de la sesión A sigue abierta.
UPDATE empleados
SET salario = salario + 100
WHERE id = 101;

Sesión A: repetir la lectura y terminar

-- Observa el valor y confirma para liberar los recursos retenidos.
SELECT id, salario
FROM empleados
WHERE id = 101;

COMMIT;

Repetir con SERIALIZABLE

-- En una nueva prueba, cambia el aislamiento antes de abrir la transacción.
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;

SELECT id, salario
FROM empleados
WHERE id = 101;

-- Coordina manualmente la consulta y el cambio desde la segunda sesión.
COMMIT;

Probar el bloqueo de tabla solicitado

-- En una sesión de pruebas, bloquea la tabla para escritura y luego libera el bloqueo.
LOCK TABLES empleados WRITE;
UNLOCK TABLES;

Haz estas pruebas solo en una base de datos de prácticas y con dos sesiones propias. En MySQL, LOCK TABLES puede provocar una confirmación implícita y el comportamiento depende del motor y del cliente; revisa cómo liberar el bloqueo antes de ejecutarlo.
